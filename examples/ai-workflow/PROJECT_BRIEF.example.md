# PROJECT_BRIEF Example

## 概要

- プロジェクト名: Support Inbox
- 一言説明: 問い合わせ対応を一元管理する社内Webアプリ
- 現在のフェーズ: Beta
- リリース単位: 2週間ごとの反復リリース

## 背景

- 解決したい課題: 問い合わせ対応がメールとチャットに分散している
- なぜ今やるのか: 対応漏れと重複対応が増えている
- 想定ユーザー: サポート担当、運用責任者

## ゴール

- 達成したい状態: 問い合わせを単一画面で受付、担当、完了まで追える
- 成功指標: 初回応答時間を 30% 短縮する

## 非機能要件

- 性能: 一覧画面は 2 秒以内に表示する
- 可用性: 平日日中の利用時間帯で安定稼働する
- セキュリティ: 社内 SSO を前提とする
- 運用監視: エラー率と未処理件数を計測する

## 非ゴール

- 今回やらないこと: 顧客向け公開ポータル
- 後続フェーズへ回すこと: FAQ 自動生成

## 制約

- 技術制約: 既存の Rails API と React フロントエンドを維持する
- 期限: 2026-06-30 までに Beta を運用チームへ展開する
- 互換性: 既存の認証基盤と監査ログ形式を維持する
- セキュリティ・運用上の制約: 権限ごとの閲覧制限を崩さない

## 現在のシステムスナップショット

- 主要コンポーネント: API、Web UI、通知ワーカー
- データの中心: inquiry, assignment, comment
- 外部依存: SSO、Slack 通知、監査ログ基盤
- 既知の弱点: 担当者の二重割り当てを防げていない

- 設計ドキュメント: `design/01-overview/summary.md`, `design/02-architecture/structure.md`

## 進め方

- 人間がレビューする判断ポイント: 権限制御、業務フローの妥当性、監査影響
- AI に任せる範囲: 調査、実装案、テスト追加、ドキュメント下書き
- 必須の検証: 単体テスト、E2E の主要フロー、権限別の手動確認
- デプロイ時の注意: 段階リリースと feature flag を前提とする
